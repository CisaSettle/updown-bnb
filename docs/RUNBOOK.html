检查与恢复

在上述生产主机执行：

systemctl status updown-keeper updown-betbot --no-pager
journalctl -u updown-keeper -n 50 --no-pager
journalctl -u updown-betbot -n 50 --no-pager

健康检查同时核对市场名称、暂停状态、余额和最近边界进度。已授权修复时重启故障服务：sudo systemctl restart updown-keeper 或 sudo systemctl restart updown-betbot；随后确认实际轮次推进和链上交易，不能只看进程存活。空市场可使用虚拟轮次而不发送交易；机器人可能为节省 gas 只覆盖一个市场。

暂停后恢复使用 unpause() 并由 keeper 继续推进，已经 genesis 的市场不要再次调用 genesisStart()。暂停不自动退款已锁定仓位；超过有效结算窗口的轮次才会退款。预言机及相位不可更换，没有 setOracle；失效喂价需按新部署处理。错误价格证明会回滚，不能直接触发退款。

浏览器错误告警

网页是纯静态的 GitHub Pages，没有自己的后端，浏览器里的错误以前没有任何人能看到。现在页面把错误签名（异常类名 + JSON-RPC 错误码，例如 unclassified/InsufficientFundsError/-32000）用 sendBeacon 发到 keeper 的 POST /client-error；keeper 只计数，计数随 /healthz 出来，由 updown-health-monitor.timer 每小时最多发一条 Telegram 摘要。签名里不含消息、堆栈、地址或金额——viem 的 message 会把请求参数（发送地址、calldata、下注金额）打印进去，所以这条链路上永远只发签名。

收到 [UpDown prod] web app: N new browser error(s) 时：这不是停机。keeper 和市场都不受影响，它只说明访客的浏览器报了错。它走独立通道，永远不会把 watchdog 判成 unhealthy，也不会占用停机告警的冷却档期。

关闭方式有两个：keeper 侧 CLIENT_ERROR_REPORTS=false（路由直接 404），或 watchdog 侧 UPDOWN_CLIENT_ALERT_COOLDOWN_SECONDS=0（仍然计数，不再发消息）。

开启需要三步：① keeper 的 /etc/updown/keeper.env 里设 CLIENT_ERROR_REPORTS=true、CLIENT_ERROR_ALLOWED_ORIGINS=https://updown.bluffking.ai 和 METRICS_SOCKET=/run/updown/keeper.sock；② texas-h5 主机现有的 Caddy 上加 TLS 前置路由（见下）；③ 在 GitHub 仓库变量里设 ERROR_REPORT_URL 后重新部署 Pages。三步没做完之前，两端都是完全静默的空操作。

Caddy 是通过 unix socket 而不是端口找到 keeper 的。本机上 METRICS_HOST=127.0.0.1（刻意锁的，不是默认值），且 ufw 默认 deny (incoming) 把容器→宿主机的路整条堵死 —— 2026-09-06 实测：即使把监听改成 0.0.0.0，deploy_web 上的容器经两个网桥网关（172.18.0.1 / 172.17.0.1）都够不到宿主机。让端口方案跑通只有两条路：绑定所有网卡、以及开一条 9464 的防火墙规则；两者都会为了暴露一个「错误上报」的旁路，去扩大持有 keeper 私钥那个进程的网络暴露面，还会把会报余额的 /metrics 变成只靠 ufw 单点拦着。socket 两样都不需要：keeper 在 /run/updown/keeper.sock 上提供同一套路由（0660 updown:updown，由 unit 的 RuntimeDirectory=updown 创建、停机时清掉），caddy 容器 bind-mount 那个目录，访问控制就是这个文件的权限本身。任何网络接口上都不多一个字节的暴露，keeper 原来的 TCP 监听完全不动，watchdog 照旧走 127.0.0.1。

第 ② 步的两处改动都在 texas-h5 仓库（deploy/），已经提交在那边的本地 main 上，但要跑那边的 deploy workflow 才生效（它会强制重建 caddy 容器）：

# deploy/docker-compose.prod.yml — caddy 服务的 volumes
      - /run/updown:/run/updown      # 必须可写：连 unix socket 需要写权限

# deploy/Caddyfile — {$APP_DOMAIN}, {$API_DOMAIN} 块内
	@updown_report {
		path /updown/client-error
		method POST
	}
	handle @updown_report {
		reverse_proxy unix//run/updown/keeper.sock {
			rewrite /client-error
		}
	}
	handle /updown/* {
		respond 404
	}

method POST 与兜底的 /updown/* → 404 一起，把对外暴露面限制成恰好一个路径一个方法；keeper 的 /metrics（会泄露 keeper 余额）不会因此上公网。

如果上报开始 502，先看这两处 —— 它们是 2026-09-06 上线时踩到的，两个都只有真机才会暴露。① unit 里 RestrictAddressFamilies 必须含 AF_UNIX，否则内核直接拒绝建 socket（listen EAFNOSUPPORT），而沙箱之外的任何测试都复现不出来。② unit 里必须有 RuntimeDirectoryPreserve=yes：RuntimeDirectory= 会在停止时删掉目录、启动时新建一个（新 inode），而 caddy 的 bind mount 钉在旧 inode 上，于是第一次重启之后容器就永远看着一个空目录，两边日志都不会说为什么。排查命令：

sudo stat -c %i /run/updown
sudo docker exec deploy-caddy-1 stat -c %i /run/updown   # 两个 inode 必须相同

inode 不一致就 force-recreate 一次 caddy。keeper 本身对此是安全的：socket 起不来只会打一条 error 日志，进程照常settle轮次。

这个端点是无认证的，且和 keeper 私钥同进程。它的边界是：请求体 2 KB 上限（边收边判，不是先缓冲再检查）、固定 schema、每分钟全局配额、签名基数上限、签名字符白名单、无论结果一律回 204（不告诉调用方什么被接受了）、不落盘、不读也不存 IP、不持有任何凭证。Origin 白名单只是降噪，不是认证——它可以被伪造。

测试币 gas 补给

整块板子持续消耗 tBNB，keeper 最多——它要推送边界喂价并结算每一轮。链上水龙头是唯一来源，且需要人工过验证码，所以补给循环是：人工领取到一个合格地址，脚本再分发出去。

机器人日志出现 FAUCET_REQUIRED，或 watchdog 报 funder … at/below reserve 时：

  1. 到 官方测试币水龙头 领取，收款地址填 funder（/etc/updown/monitor.env 的 FUNDER_ADDRESS）。官方水龙头只服务在 BSC 主网持有 0.002 BNB 的地址——这是对身份收费，不是资源稀缺——并且要人工过验证码。EVM 地址在两条链上相同，所以同一个地址可以主网持有门槛币、测试网收币。五个运营地址里只有 funder 满足这个门槛，keeper、两个 bot、owner 的主网余额都是 0。

    水龙头的发放量与规则由官方决定、随时可变，这里不写死数字，也不要假装验证码可以自动化。官方没币时（2026-09-04 出现过 The faucet has insufficient funds）改用 官方 Telegram 机器人：点 Start 后发送 I would like to get tBNB to my wallet <地址>，它不要求任何主网余额。不要用 QuickNode——它查的是 ETH 主网余额，本项目所有账户都是 0。

  2. 到账后什么都不用做：updown-betbot 正在运行时会自己把 funder 的余额分给低于下限的账户。只有在 betbot 停止时才手工分发——同一个 funder 账户上跑两个签名者会抢 nonce：

    SRC_KEY=0x… BOT_ADDRESSES=<botA>,<botB> node scripts/fund-gas.mjs --dry   # 确认后去掉 --dry

    BOT_ADDRESSES 必须给：不给的话脚本的补给目标只有 keeper，两个 bot 会被静默跳过——而它们通常正是最接近下限的账户。

fund-gas.mjs 签名前会重新确认 RPC 返回链 97：这把 key 在同一地址上控制主网真实 BNB，连错端点就是花真钱。它按目标余额补差而不是发固定金额；来源不足时所有转账等比例缩放，让整块板子同时到期，而不是喂饱前几个、饿死最后一个。

换水龙头地址时注意：/etc/updown/daily-report.env 和 /etc/updown/betbot.env 里的 UPDOWN_FAUCET_URL / UPDOWN_FAUCET_FALLBACK_URLS 覆盖代码默认值。改了代码默认值还不够，主机上的 env 文件要一起改，否则线上仍然用旧链接。

gas 紧张时的止血手段：把 /etc/updown/betbot.env 的 MARKETS 收窄到 10 分钟市场（1 分钟市场的交易频率高一个数量级；没有下注后 keeper 对应的 worker 也会转入 dormant，连边界喂价一起停）。RELAY_TICK_MS=0 关闭额外图表喂价，必需的边界喂价仍然执行。先保证 keeper 能处理已有资金的轮次。

签名与密钥保护

私钥仅存忽略的 env 文件，服务配置权限 0600。机器人仅允许链 97，机器人、keeper、owner 账户必须隔离；资金分配脚本签名前必须核对链 ID。钱包的同一地址可能持有主网真 BNB，不能删除这些保护。

Checks and recovery

Run on the production host above:

systemctl status updown-keeper updown-betbot --no-pager
journalctl -u updown-keeper -n 50 --no-pager
journalctl -u updown-betbot -n 50 --no-pager
curl -fsS localhost:9464/healthz

Check market identities, pause state, balances and recent boundary progress together. For an authorized repair, restart the failed service with sudo systemctl restart updown-keeper or sudo systemctl restart updown-betbot; then confirm round progress and on-chain transactions, beyond process liveness. Empty markets can use virtual rounds without transactions; the bot may cover only one market to save gas.

After a pause, call unpause() and let the keeper continue; never call genesisStart() again on an initialized market. Pausing does not automatically refund locked positions; rounds that miss their settlement window become refundable. The oracle and its phase are immutable, with no setOracle; a failed feed requires a new deployment. An invalid price proof reverts and cannot directly force a refund.

Browser-error alerting

The web app is a static GitHub Pages bundle with no backend of its own, so until now nobody could see an error that happened in a visitor's browser. The page now sends an error signature — the exception class names plus the JSON-RPC code, e.g. unclassified/InsufficientFundsError/-32000 — by sendBeacon to the keeper's POST /client-error. The keeper only counts; the counts ride out on /healthz, and updown-health-monitor.timer turns them into at most one Telegram digest per hour. A signature carries no message, no stack, no address and no amount: viem's message pretty-prints the request arguments — sender, calldata, the value of a real bet — so only signatures ever travel this path.

When [UpDown prod] web app: N new browser error(s) arrives, it is not an outage. The keeper and the markets are unaffected; it reports what visitors' browsers hit. It runs on its own lane, never makes the watchdog verdict unhealthy, and never consumes the incident alert slot.

Two switches turn it off: CLIENT_ERROR_REPORTS=false on the keeper (the route 404s), or UPDOWN_CLIENT_ALERT_COOLDOWN_SECONDS=0 on the watchdog (still counted, never sent).

Turning it on takes three steps. (1) Set CLIENT_ERROR_REPORTS=true, CLIENT_ERROR_ALLOWED_ORIGINS=https://updown.bluffking.ai and METRICS_SOCKET=/run/updown/keeper.sock in /etc/updown/keeper.env. (2) Add the TLS front on the texas-h5 host's existing Caddy (below). (3) Set the ERROR_REPORT_URL repository variable and redeploy Pages. Until all three are done both ends are inert no-ops.

Caddy reaches the keeper over a unix socket, not a port. On this host METRICS_HOST is deliberately 127.0.0.1 — not its default — and ufw's default deny (incoming) blocks the container-to-host path outright: measured on 2026-09-06, a container on deploy_web could not reach a host listener on either bridge gateway (172.18.0.1 or 172.17.0.1) even bound to 0.0.0.0. Making a port work would take binding every interface AND opening a firewall rule for 9464 — both widening the network surface of the process that holds the keeper's signing key, and leaving /metrics (which reports its live balance) behind ufw alone, in order to expose a side-channel for error reports. A socket needs neither: the keeper serves the same routes on /run/updown/keeper.sock (0660 updown:updown, created and cleaned by the unit's RuntimeDirectory=updown), the caddy container bind-mounts that directory, and the file's own permissions are the access control. Nothing new appears on any network interface, and the keeper's TCP listener is untouched — the watchdog still polls it on 127.0.0.1.

Both halves of step 2 live in the texas-h5 repository (deploy/). They are committed on that repo's local main and take effect only when its deploy workflow runs, which force-recreates the caddy container:

# deploy/docker-compose.prod.yml — the caddy service's volumes
      - /run/updown:/run/updown      # read-write: connecting to a socket needs write permission

# deploy/Caddyfile — inside the {$APP_DOMAIN}, {$API_DOMAIN} block
	@updown_report {
		path /updown/client-error
		method POST
	}
	handle @updown_report {
		reverse_proxy unix//run/updown/keeper.sock {
			rewrite /client-error
		}
	}
	handle /updown/* {
		respond 404
	}

method POST plus the catch-all /updown/* → 404 narrow the public surface to exactly one path and one method, so the keeper's /metrics — which reports the keeper's balance — is not exposed along with it.

If reports start returning 502, check these two first — both were hit on the 2026-09-06 rollout, and neither can be reproduced off the box. (1) RestrictAddressFamilies in the unit must include AF_UNIX, or the kernel refuses the socket outright (listen EAFNOSUPPORT) — the sandbox is what enforces it, so every test outside systemd passes. (2) the unit must carry RuntimeDirectoryPreserve=yes: RuntimeDirectory= deletes the directory on stop and creates a new one (a new inode) on start, while caddy's bind mount stays pinned to the old one — so after the first restart the container looks at an empty directory for ever, with nothing in either log to say why. To diagnose:

sudo stat -c %i /run/updown
sudo docker exec deploy-caddy-1 stat -c %i /run/updown   # the two inodes must match

If they differ, force-recreate caddy once. The keeper itself is safe either way: a socket it cannot open is logged as an error and nothing more — it goes on settling rounds.

The endpoint is unauthenticated and shares a process with the keeper's signing key. Its bounds: a 2 KB body cap enforced while streaming (not buffered then measured), a fixed schema, a global per-minute ceiling, a signature cardinality cap, a signature character allowlist, the same 204 whatever it decides (a caller is never told what was accepted), no disk writes, no IP read or stored, and no credential held. The Origin allowlist is a noise filter, not authentication — it is spoofable.

Keeping the testnet in gas

The board burns tBNB continuously — the keeper hardest, because it pushes boundary prices and settles every round. The chain's faucet is the only source and it is gated behind a captcha a human must clear, so the sustainable loop is: a person claims into one qualifying address, and a script spreads it.

When the bot logs FAUCET_REQUIRED, or the watchdog reports funder … at/below reserve:

  1. Claim at the official testnet faucet into the funder (FUNDER_ADDRESS in /etc/updown/monitor.env). The faucet serves only an address holding 0.002 BNB on BSC mainnet — an anti-sybil price on identity, not scarcity — and raises a captcha a human must clear. An EVM address is the same on both chains, so one address can hold the mainnet qualifier and receive the testnet coin. Of the five operational accounts only the funder clears that bar; the keeper, both bots and the owner hold zero on mainnet.

    The amount and policy are external and can change; do not encode a promised number here, and do not pretend the captcha can be automated. When the official dispenser is empty (it answered The faucet has insufficient funds on 2026-09-04), use the official Telegram bot: press Start and send I would like to get tBNB to my wallet <address>. It asks for no mainnet balance at all. Do not use QuickNode — it gates on an ETH mainnet balance, and every account here holds zero ETH.

  2. Once it lands, do nothing: a running updown-betbot spreads the funder's balance to whatever is under its floor by itself. Distribute by hand only while the bot is stopped — two signers on the same funder account race each other's nonces:

    SRC_KEY=0x… BOT_ADDRESSES=<botA>,<botB> node scripts/fund-gas.mjs --dry   # then without --dry

    BOT_ADDRESSES is required. Without it the script's only target is the keeper and both bots are silently skipped — and they are usually the accounts nearest their floor.

fund-gas.mjs re-checks that the RPC answers chain 97 before it signs anything: the funding key controls real BNB on mainnet at the same address, and a wrong endpoint would spend it. It tops up to a target rather than sending fixed amounts, and when the source is short it scales every transfer by the same fraction, so a partial claim leaves the whole board on one expiry instead of filling the first account and starving the last.

When changing faucet links, remember that UPDOWN_FAUCET_URL / UPDOWN_FAUCET_FALLBACK_URLS in /etc/updown/daily-report.env and /etc/updown/betbot.env override the code defaults. Changing the default in the repository is not enough — edit the env files on the host too, or production keeps using the old links.

To stop the bleeding while gas is tight, narrow MARKETS in /etc/updown/betbot.env to the 10-minute markets: the 1-minute ones transact an order of magnitude more often, and with no stake on them the keeper's workers go dormant too, which stops their boundary relays as well. RELAY_TICK_MS=0 disables extra chart ticks while keeping required boundary relays. Prioritize keeper gas for funded rounds.

Signing and key protection

Keep private keys in ignored env files and service configuration at mode 0600. The bot accepts only chain 97; bot, keeper and owner accounts must be separate. The funding script must check chain ID before signing: the same address may hold real mainnet BNB. Preserve these checks.
